# Working together

How any number of agents build this game without tripping over each other. Read it at the start of every session, after `AGENTS.md` and `docs/status.md`.

## Who's who

| Who | Does |
| --- | --- |
| The owner | Plays the game, asks for things (`owner-ask`), answers hard stops; their rulings win where they've spoken |
| Building agents, any number and any tool | Co-design and build the game with real creative freedom (`AGENTS.md` §2), one branch and one pull request per task. Claude Code sessions also start their successors (`docs/successors.md`). |
| Muse reviewer | Advisory review notes on #20. See the bulletin in #20 for topics. See `docs/muse-summary.md` only if you need the rules. No claim / merge authority. |

There is no art assistant: every model, sound and tune is made in code.

**Everyone posts as the owner's GitHub account,** so the author name can't tell agents apart. Sign every comment: Claude Code ends with its "Generated by Claude Code" footer, and other agents end with `— <tool name>`. A comment with no signature is the owner's.

## Starting a session

1. Read `AGENTS.md`, `docs/status.md` and this file.
2. **Read the board** (GitHub Issues), in the order of work (`AGENTS.md` §2): `ci-periodic`, your own open claims and handoffs, `owner-ask`.
3. **Start from the latest `main`.** Don't run the full check yet: `main`'s `ci` result covers it (read it with `actions_list`). If it's red, fixing it is your task.
4. **Pick one issue** labelled `ready`, or **pitch your own** (`.github/ISSUE_TEMPLATE/pitch.md`; before pitching blind, glance at the open `seed` issues, titles first: "Seeds" below), in a lane nobody else holds a `claimed` issue in. Check its "Depends on" line. Whichever you choose, groom the board on the way (below).
5. **Claim it** (below), then start.

## The board

The board is the repo's GitHub Issues; [#2](https://github.com/BuggsA/Ages-of-earth/issues/2) is "Start here" and the shared log. New tasks follow `.github/ISSUE_TEMPLATE/task.md`. A label is created the first time someone applies it.

**One status label each:**

| Label | Means | Moved on by |
| --- | --- | --- |
| `ready` | Free; anyone may claim it | the agent who claims it |
| `claimed` | Being worked on; the latest claim comment names the branch and date | that agent |
| `blocked` | Waiting on the issue named on its "Depends on" line | whoever finishes that issue |
| `owner-decision` | Waiting on the owner, for a hard stop only (`AGENTS.md` §3) | the owner, by answering |
| `in-review` | Built and pushed, pull request open | its agent, by merging |

**One lane label each** (next section): `lane:rules`, `lane:ai`, `lane:look`, `lane:online` or `lane:tooling`.

**Others:** `pitch` (an agent's own idea), `owner-ask` (something the owner asked for; it goes before pitches), `umbrella` (a feature split into steps), `effort:hard` (needs the stronger model, `docs/successors.md`), `ci-periodic` (opened by the scheduled check), `start-here`, `seed` (an idea nobody is building yet: "Seeds" below).

## Seeds

Ideas nobody is building yet, for anyone to grow. Reading them is optional and cheap: list open `seed` issues by title, then open only the ones that catch you.

- **Plant:** one issue from `.github/ISSUE_TEMPLATE/seed.md`, five lines at most, **Player does** and **Changes a choice** filled in. One new seed per session. At most 12 open: whoever opens the 13th closes the oldest as not planned, with "Retired at the cap", and it stays searchable.
- **Build on:** one reply per agent per seed, three lines at most, adding a connection, a twist, or a problem *with* its fix. No debate and no second round; a 👍 says "I'd play this". The owner's and the Muse's replies steer.
- **Grow it into work:** no approval needed. Open a `pitch` issue that links the seed, fold in the best build-ons, close the seed as completed with that link, and build as usual.

## Lanes

A lane is a set of files two agents shouldn't edit at once. Steps in one lane run one after another; lanes run side by side.

| Lane | Its hot files | Typical work |
| --- | --- | --- |
| `rules` | `src/sim/` except `ai.ts`, `tests/` | new units, buildings, technologies, orders, game modes |
| `ai` | `src/sim/ai.ts`, `scripts/sim.ts` | how the computer plays |
| `look` | `src/render/`, `src/audio/` | models, effects, sound, music, with no rule changes |
| `online` | `worker/`, `src/net/`, `src/ui/lobby.ts`, `wrangler.toml` | rooms, the lobby, rejoining, replays over the wire |
| `tooling` | `.github/`, `.claude/`, configs, the docs in this list | CI, checks, the process |

- **Gameplay features cut across lanes.** In this codebase a new unit touches `data.ts`, `units.ts`, its model, the HUD and `main.ts` together. Its lane is where its main change is, almost always `rules`; name the other lanes' hot files it edits in the claim, and if another lane's open pull request edits the same functions, wait for it to merge. So in practice: one `rules` step at a time, beside one step in `ai`, `look` or `online`.
- **Shared files** (`src/sim/data.ts`, `src/sim/types.ts`, `src/ui/hud.ts`, `src/main.ts`, `index.html`, `README.md`, `docs/status.md`): add your own entries and don't reorder or reformat anyone else's, so merges stay clean.
- **Feature steps.** A feature too big for one session gets an `umbrella` issue with its steps as a checklist, and one issue per step (`Trade ships s1: the trade cog and its route`). A pull request that only writes a plan says `Refs #N`, never `Closes #N`. Keep step issues open for the next two steps; later ones wait on the umbrella's checklist.

**Grooming,** by whoever finishes a step or finds nothing `ready`: tick the step off its umbrella and open the next; move a `blocked` issue to `ready` once what it waited on has merged; list what each `owner-decision` issue is waiting on in one comment on #2.

## Claims, handoffs and takeovers

Sessions end without warning, so claims are built for that.

- **Claim:** comment `Claiming: branch <name>, <date>. Lane: <lane>. Files: <list>.` and swap the label to `claimed`. Hold one claim at a time.
- **Check you won it.** About 10 seconds later, re-read the comments. If another `Claiming:` comment has a lower comment id, it won: comment `Withdrawing: claimed first by <branch>` and pick another issue.
- **Hand off at the end of every session,** finished or not, after pushing, in about 20 lines with links rather than pasted text:
  ```
  Handoff: branch <name>, last commit <sha>, <date>.
  Done: …
  Not done: …
  Next step: …
  Gotchas: … (three lines at most)
  Watching: … (subscriptions and check-ins, which end with your session)
  Successor: … (Claude Code: docs/successors.md; other tools: "none, the owner starts the next")
  Claim: kept / released.
  ```
  A released claim goes back to `ready`.
- **Stale claims:** a `claimed` issue with no comment and no push for **24 hours** may be taken over. Comment `Taking over from <branch>`, merge that branch into yours, and carry on from its last handoff. Never push to another agent's branch.
- **Owner rulings** count when they quote the owner and say where (an issue link, or "the owner's chat with <tool>, <date>"). A paraphrase isn't a ruling: ask on the issue. New rulings go at the end of `docs/rulings.md`.
- **Finish:** open a pull request into `main` with `Closes #<issue>` and the `## Verification` section, swap the label to `in-review`, and merge it yourself once "Merging" (below) allows.

## Branches

- **The base is `main`.** Work reaches it only by merged pull request; nobody pushes to it directly, docs included.
- **One branch per task, one pull request,** named `claude/<issue>-<topic>` (other tools: `<tool>/<issue>-<topic>`). A merged branch is finished: the next task starts a new branch from `main`. Sessions whose branch name is set by their harness keep it.
- **Needing another agent's unfinished work:** merge their branch into yours and say so on their issue. Merge, never rebase, other people's commits.
- **Small and often.** One step, one pull request, merged in the same session. A branch that lives for days collects conflicts.

## Merging

`main` is what players get. Agents merge their own pull requests when all of this holds:

1. It's your pull request, for an issue you claimed.
2. It merges cleanly into `main`, and `ci` ran on it (a pull request's `ci` tests it merged with `main`). If `main` moves while you wait, merge it again only for a conflict or a red check: `ci` on `main` catches the rest, and Revert undoes it.
3. `ci` is green on that exact commit; you ran `npm run check` and the slow tests that cover your change (`AGENTS.md` §5); the `## Verification` section has the real output. A check that fails once and passes on a re-run is not a pass: say so in the pull request.

   **Cloudflare's "Workers Builds" check is not a gate.** Agents can't read its log, `ci` runs the same build, and a failed Cloudflare build deploys nothing, so the live game stays as it was. When it fails, say so in the pull request and on #2, so the owner can read the log in the Cloudflare dashboard. (It failed on every branch until `[previews]` was added to `wrangler.toml` in #23; it has passed since.)
4. Nothing in it is a hard stop, or the owner approved that part in their own words. Flags don't block.
5. Merge with a merge commit. Never force-push or rewrite `main`, and never delete branches, tags or issues that aren't yours.
6. After merging, comment the pull request link on the issue.

**If `main` breaks:** open the merged pull request on GitHub and press **Revert**, merge the revert, then fix forward on a new branch.

## Saves and replays

A saved match is the whole game state, wrapped as `{ v: 1, … }` by `saveGame` in `src/main.ts`; `loadGame` ignores a save whose `v` differs. A replay is the setup and the command list. Neither records the build that made it, so a change to the state's shape can break an older save, and any rules change can make an older replay play out differently. Until the owner rules otherwise (`docs/status.md`), that's allowed and flagged in the pull request, with one duty: **if your change can break an older save, bump `v`**, so the old save is set aside instead of loading broken. Claim the bump on #2 first, one bump open at a time. Cloud saves (#290) hold the same save text with the same `v`, so the rule covers them too.

## Working without rework

1. Before claiming, look at the open pull requests' files. If yours would change the same functions, build after that one merges, or on top of its branch (say so on its issue), or pick other work.
2. When a pull request that touches your files merges, merge `main` into your branch at once.
3. Read the rulings (`docs/status.md`, `docs/rulings.md`) before building: work against a ruling gets thrown away.
4. Never make the game worse to save tokens, and never spend them twice on the same work.
